# 以 Claude Code 建置「組織法規與編制表查詢比對系統」的提示工程歷程分析

行政院人事行政總處　組編人力處　教學報告（2026 年 11 月 9 日）

---

## 壹、專案概述

### 一、目標
把雲端硬碟中以 AI 彙整的「組織法與編制表」資料，經與全國法規資料庫核對後，建成可查詢、可同級比對（例如海洋保育署與其他三級署的副組長、簡任非主管比）的系統，並設計法規異動時的更新流程與操作手冊。

### 二、成果數據（2026-10-31 至 11-07，三個工作日）

| 項目 | 數值 |
|---|---|
| 收錄機關 | 585（編制表明細 13,380 列、條文 20,014 條） |
| 資料狀態 | 可用 576、可用（條文區間）5、可用（區間）3、不適用 1；未取得由 16 降為 0 |
| 不可比較機關 | 由 41 降為 1（駐外機構，依指示排除） |
| 人工修正紀錄 | 374 筆，每筆附來源、頁碼、對源說明 |
| 程式規模 | 核心五支程式約 1,600 行；測試五套 175 項（資料層 84、P1 單元 27、控制列 9、dry-run 17、前端 38） |
| 版本管理 | 43 次提交、2 個經審查合併的 PR、GitHub Pages 自動發布；每版附來源提交編號與 SHA-256 |
| 維護文件 | 45 份（診斷計畫、實作紀錄、測試日誌、人工確認清單、來源副本） |

### 三、使用工具
Claude Code（雲端工作階段）、Python（pandas、pdfplumber）、單檔 HTML（資料內嵌、離線可用）、Playwright 前端測試、GitHub（分支、PR、Actions、Pages）、全國法規資料庫開放資料、教育部與法務部網站。

## 參、使用者提示策略分析

本案最值得教學的，不是程式，而是使用者如何用提示把一個容易失控的資料工程任務收斂成可審查、可回滾的流程。歸納出七種策略。

### 一、流程先行：診斷、書面同意、分支、PR 四段鎖
原文要旨：「本批只改分支、跑測試，不合併、不部署」「PR 僅供檢視差異，建立 PR 不代表同意合併或部署」「完成診斷後停止，等待我書面同意實作」。

效果：AI 每一批工作都以「計畫 → 同意 → 實作 → 測試 → 兩階段提交 → PR」進行，任何一步都可中止。十個階段中沒有一次未經同意就改動線上版。

教學重點：把「什麼時候可以動資料、什麼時候可以上線」寫進提示，比事後糾錯便宜得多。

### 二、限制優先於方案
原文要旨：「同意實作 P1，以下限制優先於原診斷方案」，接著列 A～D 四組限制，例如「區間不是括號語意」「unknown 只指括號部分，專任照常計入」「原文 raw 不得覆寫」。

效果：AI 的診斷方案若與限制衝突，以限制為準，避免 AI 自作主張簡化問題（例如把區間下限直接當定額）。

### 三、證據門檻
原文要旨：「人工補登需來源、頁碼、逐列對源」「語意命中須標待審，不可靜默刪列再把剩餘加總當總額」「表內驗算不等於官方來源核對」「539 份 PDF 掃描只稱本批資料範圍，不宣稱涵蓋全部現行法規」。

效果：每筆人工修正帶 FileId 與頁碼；品質註記、來源核對、驗算結果三者分欄；報告用語受限（不說「已人工點過」，只說「結構掃描」）。

### 四、不假設、先盤點
原文要旨：「先診斷現有專案的更新能力，不假設 repo 已存在 manifest、依賴圖或 update 指令」「命令名稱只是待設計介面，不代表已實作」。

效果：AI 逐檔盤點現有九支程式與入口，列出「已有／缺少」，才提規格；避免憑印象描述不存在的功能。

### 五、縮小範圍
原文要旨：「只修下列三項。先確認現有函式／資料欄與受影響清單，再做最小 diff。不要重爬全庫、重 OCR、重算已人工核定數值、重建整站；不要順手展開其他 P2」。

效果：該批 5 個檔案、55 行新增、指標差異 0 筆；測試全綠；驗收容易。

### 六、領域知識注入與邏輯澄清
原文要旨：「委員欄位（3～5）實際上是兼任委員人數，不計入專任，但要保留規模」「醫師、中醫師、牙醫師共用員額 300 人，由醫院自行判斷」「人事、主計、政風一條鞭，編制表會先有一直列寫單位名稱」「警大警專是雙軌制，警備隊另外獨立參考」「組織法內明定聘用及約僱人數是特例，可能是員額超過 5% 的原因之一」。

效果：這些是 AI 單靠資料無法確定的語意，使用者一句話就把規則定下，AI 轉成可測試的程式規則（794 列合併計列、6 個單位標題列、50 列單位重組、12 個聘用約僱特例機關）。

### 七、分工與減量
原文要旨：「你先處理邏輯，等你處理完我再人工作業，不然你也列出太多了」「其餘沒打勾的部分我看不懂你的陳述，但邏輯是你的建議沒錯，就先照你的建議修正」「像是無法轉檔判斷的部分，你先做一版，我用人工核對調校」。

效果：人工確認清單由 42 個機關減為 27 個，再減為 4 個轉錄待核加 8 個候選修正；人只做勾選與口徑判斷。

## 肆、AI 端的工作方法與可觀察的行為

1. 每批先重算受影響清單與前後差異，再改碼；改碼後以舊產物為基線跑回歸，列出每一筆指標變動並分類（例如 P1 的 187 筆：括號語意 140、碎片列 18、區間 1、其他 28），「其他」類必須逐筆解釋。
2. 兩階段提交：先提交程式（來源提交），再建頁並提交產物，頁首顯示來源提交編號；離線 zip、私人預覽、分支檔三者同一 SHA。
3. 把人工判斷轉成資料而非程式分支：人工修正放 `manual_fixes.json`，含來源與頁碼；審查指示（軍備局只採文職表、駐外機構排除）也以帶註記的資料動作記錄，可追溯、可回滾。
4. 測試隨規則成長：每個新規則都附正例與反例（例如氣象站 30 筆不得被啟發式誤判為錯掛；退輔會不得因名稱含「軍」被排除）。
5. 誠實標示能力邊界：影像 PDF 沒有 OCR 工具時，以頁面影像人工轉錄並標「請核對」；合計推算值（八德外役監獄科長 4 人）明寫「為推算，請抽查」。

## 伍、失誤案例與修正（教學用）

| 案例 | 發生原因 | 被誰發現 | 修正方式 |
|---|---|---|---|
| 名稱含「軍」就排除為軍事機關，退輔會 42 個機關被誤排 | 以名稱單字判定 | 使用者 P2 指示 | 改依部會欄（機關代碼系統）判定並附依據 |
| 多部法規的連結以全形「；」串在同一個 anchor 裡 | 建表時串接欄位，前端直接輸出 | 使用者 | 拆成來源陣列，數量不符則待審、不猜配 |
| 把全國法規資料庫的「無附件」當成「無編制表」 | 只查附件連結，未查獨立的編制表法規頁與他部會法規網 | 使用者看到藝教館網頁版編制表 | 擴大來源：教育部法規網 HTML 表、法務部網站整合檔 |
| 臺中醫院附件 404 標為「官方合計待核」 | 用了過期 FileId | 使用者質疑網址有誤 | 找到新版附件，逐列比對相同後更新來源與按鈕 |
| 報告寫「852 列」合併計列 | 診斷表的分類加總筆誤（實為 865） | 使用者要求當證據待補 | 以兩種定義重新計數並列清單 |
| 以「單位欄」判斷單位主管 | 單位欄只有 28% 有值，主表為全機關合計列 | AI 自己驗證資料後發現 | 改以職稱清單分五類、互斥 |
| 前端面板用了不存在的變數名 | 變數名記錯 | 自動化測試（頁面錯誤、元素找不到） | 修正並加面板測試 |
| 多筆改列覆寫了「原始列」 | 第二筆修正把第一筆改後的值當原值 | 回歸測試 | 原始列只記第一次修正前的值 |

教學重點：使用者的質疑多數是「網址有誤再查一下」「邏輯是否哪裡沒設定好」這種具體而非情緒的回饋，AI 才能定位到規則層而不是逐筆硬改。

| 必須由人決定 | 可由 AI 自動完成 |

| 是否合併與部署 | 兩階段提交、PR 說明、SHA 對照、預覽 |

## 柒、可重用的提示範本

1. **啟動診斷**：「以現行 <提交編號> 為基準，只查核、提出計畫，不修改程式或資料、不合併、不部署。請交付各項根因、受影響清單、官方來源、擬改規則、預期差異及回歸測試計畫。完成診斷後停止，等待我書面同意實作。」
2. **同意實作並加限制**：「同意實作 <批次>，以下限制優先於原診斷方案：…。維持草稿分支，不合併、不部署。交付：受影響清單、判定證據、前後差異、回歸測試結果、附提交編號的離線 HTML。」
3. **縮小範圍**：「以 <提交> 為基準，只修下列 N 項。先確認現有函式／資料欄與受影響清單，再做最小 diff。不要重爬、重 OCR、重算已核定數值、重建整站；不要順手展開其他項目。」
4. **證據要求**：「人工補登需附來源、頁碼、逐列對源；語意命中標待審，不得靜默刪列；表內驗算與官方來源核對分開；掃描範圍只稱本批資料範圍。」
5. **不假設**：「先盤點現有的 <能力>，不假設 repo 已存在 <檔案／指令>。先交：有哪些檔案與入口、哪些能力已有、哪些缺少，再提最小規格。命令名稱只是待設計介面。」
6. **領域規則澄清**：「<欄位或現象> 實際上是指 <語意>，規則應為 <處理方式>；但要保留 <資訊> 以利後續查照。」
7. **分工減量**：「你先處理邏輯，等你處理完我再人工作業；真的都不行再讓我來。無法判讀的部分你先做一版，我用人工核對調校。」
8. **口徑決定**：「<機關> 不加入 <分表>，只用 <某表>；<機關> 為特殊組織，員額合計為 <值>（兼任 <範圍>）。」
9. **驗收與部署**：「驗收通過，同意合併部署，請繼續作業。」
10. **更新作業（系統內建）**：「請執行組織法編制表更新作業：先 dry-run 並給我差異摘要；等我書面核准機關清單後，才對清單機關更新、處理 override 待審、建檔、開 PR；不合併、不部署。」

## 捌、教學重點與建議

1. 流程條件寫在提示裡，比寫在腦子裡有效：四段鎖（診斷、同意、分支、PR）讓每一批都可停、可退。
2. 限制與證據門檻是品質的來源：AI 會自然傾向「讓數字對起來」；明確禁止硬湊等式、靜默刪列，才能得到可審計的結果。
3. 把領域知識當規則交給 AI，而不是逐筆改數：一句「委員括號是兼任人數規模」解決了 30 列、29 個機關。
4. 人工清單要先讓 AI 做減量與預填，人只做勾選；本案 42 個機關的清單最後只需人工核對 4 份轉錄與 8 組候選。
5. 來源不足時要求 AI 擴大來源而非猜測：教育部法規網、法務部網站整合檔各補齊兩到四個機關。
6. 每一版都要能對照：來源提交、產物提交、SHA-256、離線檔與線上頁一致，驗收才有依據。
7. 更新機制設計上，監測與發布必須分開：dry-run 只產報告，核准後才動資料，合併才發布。
